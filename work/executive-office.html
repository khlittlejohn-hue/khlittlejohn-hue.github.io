Case Study 03 · KLJ Ventures · 2026 to presentPractical AI workflows and quality controls

AI workflows for research, analysis and executive briefs.

KLJ Ventures is my AI systems practice, and I designed, built and operate the system of 120+ specialized AI agents that does its research, analysis and writing. Its clearest work product is a client deliverable, a strategic growth blueprint of roughly 60 pages with an accompanying executive briefing, and I approve every output before it leaves.

01The work

What the system produced for a client

The blueprint and briefing came from one client engagement. 2 calls from that work are described here without the client’s name or figures, because the reasoning is the part that transfers.

An acquisition cost with an undefined denominator

In client analysis I held an acquisition-cost figure as a channel cost until its denominator was defined. A cost per acquired customer means little until it is clear who counts as an acquired customer, and labeling it a channel cost kept the figure in the analysis without letting it stand for more than it showed. In the same section, I drew months with no reported data as a dashed line, so the chart did not suggest a trend for months nobody had measured.

3 ways to reach one revenue target

I laid out 3 illustrative revenue compositions that would each reach the target, and showed that each implied a different company, hiring plan and financing story. The compositions were labeled as illustrations, not forecasts or recommendations. The fastest path to the target and the strongest financing profile were not the same path, and I think naming that tension was the most useful thing the section did.

The blueprint also labels claims by how well they are supported, so a reader can tell a verified figure from a company-reported one or an open question.

02Challenge

Work I would put my name on

KLJ Ventures is a one-person firm, so the volume of research and writing has to come from a system. Getting an AI model to produce a draft is easy. Getting it to produce work I would sign, repeatedly, is harder. An assistant that is right 90% of the time and gives no signal about which 10% is wrong still costs 100% of the review.

Using AI to write more first drafts is where I started, and it only produced faster first drafts. The problem worth solving was making review reliable enough that my own attention could go to judgment.

03What I built

How work moves through the system

An agent here is a role defined in its own file, with a name, instructions, permitted tools and a model tier, that Claude Code runs when work is routed to it. I designed and operate 120+ of them across 14 functional domains. Work moves like this:

  1. A request is classified by type and routed to the domain that owns it, where the research starts.
  2. Specialized agents draft the analysis or the document.
  3. The agent that drafts is not the one that approves. Separate reviewers check the work, and on anything consequential a reviewer is instructed to look for reasons to reject it.
  4. In my most heavily used pipeline, 150+ automated checks are defined for written deliverables, and each deliverable runs the checks that apply to it before it reaches my review.
  5. I approve every output before it leaves the system.
  6. When something fails in real use, I document it, work out which class of error it belongs to, and encode the fix as a check or a written rule, so the same class of error is caught if it recurs.

04Decision

Treat every fabrication as a bug

The common framing is that language models hallucinate, that this is inherent, and that the person reading the output should check it carefully. That framing locates the problem in the technology. I located it in the system built around the technology, because that is the part I can change.

I decided to treat every fabrication as a bug: a specific defect with a cause, a reproduction case and a fix that could be encoded, so the same class of error is caught if it recurs. One example: a pre-publication audit caught a number my own system had invented in a paragraph arguing the system catches invented numbers, and the claims checker now blocks that class.

The tradeoff is cost. Every check adds time to each run and something to maintain, so the set of checks mostly grows, and checks that stop earning their cost get retired.

05Results

What the evidence shows

  • A client deliverable: a strategic growth blueprint of roughly 60 pages and an accompanying executive briefing designed to be read in one sitting.
  • 120+ specialized AI agents across 14 functional domains, in daily use within my practice.
  • 150+ automated checks defined for written deliverables in my most heavily used pipeline.

These figures describe how the system is built and what it produced. The evidence is the client deliverable and the counts above. Adoption and business results belong to the client. The system is operated by one person, for one practice.

06What carries forward

Design the checks in from the start

The first version treated review as a light final step. The rebuild put review and automated checks at the center, and I would design them in from the first version. It is the same conclusion I reached about the intake system and meeting cadence on the AMC Networks account: put the structure in place before the problems make the case for it.
